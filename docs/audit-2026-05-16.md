## 1. Duplicate `run_step` — NOT identical

Both `profiles/uefi.nu:21` and `profiles/kboot.nu:23` define `def run_step [step: record, dry_run: bool]`.

**They are NOT the same function.** The key difference is the platform gate:

| File | Platform check | Condition to execute |
|---|---|---|
| `profiles/uefi.nu` | `(^uname -s) == "FreeBSD"` | Only runs on FreeBSD |
| `profiles/kboot.nu` | `(^uname -s) == "Linux"` | Only runs on Linux |

This is intentional and load-bearing: uefi builds must run on FreeBSD (for `mdconfig`, `newfs`, etc.); kboot builds must run on a Linux host (for `sgdisk`, `mkfs.ext4`, `kexec`). The duplication is correct given Nushell's file-scope `source` semantics — there is no shared lib mechanism that would let both profiles share a single definition while each maintaining a different platform gate.

**Recommendation**: Add a comment to each file explaining the intentional divergence, to prevent future "cleanup" from merging them incorrectly. No removal warranted.

## 2. Dead code: `check-vultr-cli` in `adapters/vultr.nu`

`adapters/vultr.nu` defines `def check-vultr-cli []` at line 5. It is called internally at line 93 within `vultr_deploy` (the `# --- Credential and tool checks ---` section).

**However**, `genoa.nu` does **not** use `check-vultr-cli` for any of its Vultr-related subcommands. It uses `find_vultr` (defined in `genoa.nu:1611`) instead. `find_vultr` and `check-vultr-cli` do the same job — locate the vultr CLI binary — but with different search strategies:

| Function | File | Strategy |
|---|---|---|
| `check-vultr-cli` | `adapters/vultr.nu:5` | Checks `/opt/homebrew/bin/vultr`, `/opt/homebrew/bin/vultr-cli`, then PATH for both names |
| `find_vultr` | `genoa.nu:1611` | Checks `/opt/homebrew/bin/vultr`, then `which vultr` |

`check-vultr-cli` is only called by `vultr_deploy`, which is itself only called from `main deploy` in genoa.nu (line 352). It is not dead code in the strict sense — it is reachable when `genoa deploy` dispatches to the vultr adapter. But it is a **duplicate of `find_vultr`** (see item 4 below).

**Status**: reachable, not dead — but duplicated.

## 3. `adapters/oci.nu` and `adapters/oci-shim.nu` — ARE used

The deploy dispatch in `genoa.nu:320-366` maps `deployment_path = "byoi-api"` to `"adapters/oci.nu"`. When `byoi-api` is selected, genoa invokes `adapters/oci-shim.nu` as a subprocess (line 360), which in turn sources `../formats/convert.nu` and `oci.nu` before calling `oci_deploy`.

The shim is a deliberate workaround for a Nushell issue: sourcing `oci.nu` inside an `if/else` branch caused a closure leak to stdout. The subprocess boundary cleanly isolates this.

**Key finding on scope mismatch**: The catalog has **17 providers** with `deployment_path = "byoi-api"`:
`aws`, `gcp`, `oci`, `alicloud`, `tencentcloud`, `ibmcloud`, `digitalocean`, `hetzner_cloud`, `scaleway`, `ovhcloud_public`, `ovhcloud_dedicated`, `contabo`, `coreweave`, `crusoe`, `arp_networks`, `orionvm`, `mythic_beasts`

But the deploy dispatch routes **all** `byoi-api` providers through `adapters/oci.nu`. This means a deploy request for `digitalocean`, `hetzner_cloud`, `aws`, etc. will invoke the OCI adapter (qcow2 → OCI Object Storage → OCI custom image → OCI instance launch), which is **wrong** for non-OCI providers. The comment in the deploy dispatch says `"byoi-api" => "adapters/oci.nu"` — this should be `"oci"` only, not a generic byoi-api handler.

**`adapters/aws.nu` and `adapters/gce.nu`** are sourced at the top of `genoa.nu` (lines 8–9) but their exported functions `aws_deploy` and `gce_deploy` are **never called** anywhere in genoa.nu or any other file. They are stub adapters. They are not dead in the sense that they are intentional stubs, but they contribute to namespace pollution on every `genoa.nu` load without being invoked.

**Status**: `oci.nu` + `oci-shim.nu` are in active use. `aws.nu` and `gce.nu` are sourced but never called.

## 4. `find_tool` in `publish.nu` vs `find_vultr` in `genoa.nu` — duplicate pattern

`publish.nu:16` defines `def find_tool [name: string]`:
- Checks `/opt/homebrew/bin/<name>` first
- Falls back to PATH search via `$env.PATH | split row | each { path join } | where { path exists } | first`

`genoa.nu:1611` defines `def find_vultr []`:
- Checks `/opt/homebrew/bin/vultr` first
- Falls back to `which vultr | get 0?.path?`

`adapters/vultr.nu:5` defines `def check-vultr-cli []`:
- Checks `/opt/homebrew/bin/vultr` and `/opt/homebrew/bin/vultr-cli`
- Falls back to PATH iteration for both `vultr` and `vultr-cli` names

These three are all doing the same thing. `find_tool` in `publish.nu` is the most reusable (generic name argument), but it is private (`def`, not `export def`) and lives in a file invoked as a subprocess — it cannot be called from `genoa.nu` without a `source publish.nu` (which genoa avoids intentionally, using subprocess invocation instead).

**Recommendation**: If/when a shared lib is introduced, consolidate into a single `find_tool [name: string]` exported from a `lib/tools.nu` or similar. Until then, `find_vultr` and `find_tool` serve different call sites and cannot be trivially merged without restructuring the subprocess boundary.

### Specific issues found:

**A. `catalog` and `schema` — no `action` field, no envelope**

Both return raw file contents piped to `to json`. An agent cannot distinguish a catalog response from a schema response by inspecting the payload — there is no `action` field or wrapper. Per the AX-first design requirement, every result should carry a parseable attestation/provenance envelope.

Suggested fix for `catalog`:
```nushell
{action: "catalog" schema_version: "1.0.0" providers: (open "catalog/providers.v1.json").providers} | to json --indent 2
```

**B. `verify-image` — missing `--dry-run`**

`verify-image` mounts a disk image via `mdconfig` and `mount`, then unmounts. It has side effects (kernel state changes, mount table) and should offer `--dry-run` to return the planned checks without executing. Currently absent.

**C. `status` — missing `--dry-run`**

`status` calls `find_vultr` and runs `vultr snapshot list` and `vultr instance list`. These are API calls with real network side effects. A `--dry-run` flag that skips the Vultr API calls and returns static/cached state would align with the pattern established by other subcommands.

**D. `watch` — missing `--dry-run`**

`watch` enters a polling loop that calls the Vultr API up to N times. It should support `--dry-run` to return the poll plan without executing.

**E. `publish_image` in `publish.nu` — successful return paths lack `action` field**

The success paths in `publish_r2`, `publish_s3`, `publish_gitea`, and `publish_local` return records with `{url, sha256, size_bytes, backend, expires_at}` — no `action` field. The `main publish` wrapper in genoa.nu relays this output. Agents checking `result.action` will get `null` on success, which is inconsistent with every other subcommand that returns `action: "published"` or similar on success.

**F. `main []` (no-arg help) — prints to stdout, not JSON**

This is a deliberate human-readable help surface, but it means piping `nu genoa.nu | from json` will fail. Not a bug per se, but worth noting if the `main []` path needs to become agent-consumable (e.g., add a `--json` flag that returns a structured command listing).

### Highest-priority fixes

1. **Dispatch bug** (`genoa.nu:323`): `"byoi-api"` is too broad. The match should check `$pid == "oci"` specifically. Other byoi-api providers need their own adapters or an explicit `action: "not-implemented"` return — not the OCI flow.

3. **`catalog` / `schema` envelopes**: Wrap in `{action: "catalog", ...}` / `{action: "schema", ...}` so agents get a consistent top-level `action` field.

4. **`publish_image` action field**: Add `action: "published"` to all success return paths in `publish_r2`, `publish_s3`, `publish_gitea`, `publish_local`.
